# 演示契约：先决定观众变化，再决定页面

生成路线在写 `deck.json` 前读本文件。它只管“这份演示为什么存在、每页要推动什么、怎么讲和怎么验”，字段细节仍以 `deck_schema.md` 为准，版式容量以 `layouts.md` 和脚本为准。

## 1. 整体沟通契约

先把下面六件事写进 `meta`，不要直接从“想要几页”跳到排版。

| 字段 | 回答的问题 |
|---|---|
| `scenario` | `oral` 口播视频、`talk` 现场演讲、`reading` 发出去读、`report` 工作汇报 |
| `audience` | 谁看，已经知道什么，最在意什么 |
| `objective` | 这份演示要完成什么任务 |
| `audience_outcome` | 看完后，观众应知道、相信或做什么 |
| `storyline` | 从起点到结论的一句话逻辑链 |
| `duration_minutes` | 目标总时长；没有明确时长就省略 |

`objective` 是作者要完成的事，`audience_outcome` 是观众发生的变化。两者不能写成同一句空话。

## 2. 每页契约

每页除了观众看见的内容，还要保留以下规划字段：

```json
{
  "n": 3,
  "id": "problem-cost",
  "type": "stats",
  "rhythm": "dense",
  "purpose": "证明问题已经值得马上处理",
  "audience_move": "从觉得麻烦变成认为不处理会持续损失",
  "title": "重复劳动每周吞掉 18 小时",
  "notes": {
    "talk": ["先解释统计口径", "指出损失集中在哪两个环节", "停一下让数字被看见"],
    "transition": "既然代价已经明确，下一页回答问题卡在哪里",
    "minutes": 0.8
  },
  "source": "内部工时记录，2026 Q3"
}
```

- `id`：小写英文 slug，语义稳定；页面重排时不改，只有页面任务彻底改变才改。
- `purpose`：这页在整场叙事中的工作，不上屏。
- `audience_move`：观众看完这一页前后，认知、信念或行动意愿的变化。
- `rhythm`：`anchor` 结构锚点、`dense` 信息推进、`breathing` 留白/转折。省略时脚本按页型推断。
- `notes`：两条路线都优先用结构化对象；旧稿备注只作参考素材，不约束新备注。
- `source`：数据、事实和引文的可追溯来源；不知道就不写该事实。

一页如果既没有新的 `audience_move`，也没有必要的结构作用，就合并、重写或删除。

## 3. 故事线与消费方式

- `oral` / `talk`：一页一个判断，屏幕只留结论、证据和结构，展开内容进备注。
- `reading`：页面脱离演讲者也能独立读懂，允许更完整的上下文和来源。
- `report`：先给结论与决策，再给证据、方案、风险和下一步。

常用主线：

- 讲解：反差钩子 → 定义 → 为什么重要 → 怎么运作 → 怎么用 → 边界 → 行动。
- 决策：结论先行 → 现状证据 → 选项比较 → 推荐方案 → 风险与资源 → 需要拍板。
- 教学：学习目标 → 已知连接 → 示范 → 分步练习 → 常见错误 → 检查理解 → 总结。
- 叙事：起点 → 冲突 → 证据升级 → 转折 → 新框架 → 收束。

## 4. 节奏与版式

先排页面任务和节奏，再挑版式。页型服从内容关系，不为“多样”而硬换。

- `anchor`：封面、目录、章节、结尾；建立位置或阶段。
- `dense`：数据、比较、流程、框架、截图讲解；推动信息。
- `breathing`：大问句、大引文、单一判断、大数字；让观点停一下。
- 避免连续四页 `dense`；避免连续三页同页型或同主体结构。
- 长稿每 3–5 个内容页安排一次结构锚点或呼吸页，但不要为了配额插空页。
- 版式装不下时依次处理：换更合适的版式 → 拆页 → 精简到备注 → 最后才小幅降字号。不要靠缩到不可读硬塞。

## 5. 图片先定角色和槽位

图片不是装饰配额。写提示词或处理截图前，先判断角色：

| 角色 | 默认处理 |
|---|---|
| 证据截图 / UI / 代码 / dashboard | 保真优先，`contain`，关键文字和数据不能裁 |
| 按槽位生成的插画 / 信息图 | 按 `plan.json` 的 `image_slot` 与 `aspect_ratio` 铺满 |
| 照片 / 产品图 / 人物图 | 明确焦点和裁切位置，主体不可被标题压住 |
| 文字压图的主视觉 | 图片至少保留约 30% 低细节 quiet zone，否则换图或改分栏 |
| 多图组 | 比例、高度、容器和 caption 密度统一 |

生成图只是页面素材，不能自带页眉、页脚、页码、主标题、logo 或装饰边框。图片里的文字越多，越应该改用 PowerPoint 原生文本、形状和图表。

## 6. 演讲备注与时长

结构化 `notes` 的核心字段：

- `talk`：默认 3–5 条提词卡，每条只表达一个意思；用户明确要逐字稿时才写长稿。
- `transition`：解释下一页为什么紧接着出现，不写“下一页我们看”。
- `minutes`：计划讲述时长，不等于自动翻页。
- `cue`、`interaction`、`delivery`、`advance`、`fallback`、`pronunciation`：只有素材或用户明确提供时才写，不猜现场事实。

有目标总时长时，每页都给 `minutes`，计划总和不超过目标的 90%，给停顿、互动和意外留余量。`build_deck.py` 会把结构化字段整理为 PowerPoint 备注页里的清晰分区。旧稿字符串备注只作为重写素材，默认不会进入成品；如果没有重写为结构化对象，就留空并由检查报告提醒。只有用户明确要求并设置 `meta.preserve_notes: true` 时才原样保留。

## 7. 检查顺序

1. 幽灵稿：只读标题能否形成完整故事。
2. 页面契约：每页 `purpose`、`audience_move`、稳定 `id` 是否成立。
3. 事实：数据、图表和引文是否有来源，结论是否和数据一致。
4. 容量：先换版式或拆页，再动字号。
5. 节奏：是否出现四页连续 `dense`、三页同结构或长时间没有锚点。
6. 演讲：备注是否补充而非复述，转场是否自然，时长是否留出 10% 缓冲。
7. 视觉：以实际渲染图为准；脚本通过不代表页面已经好看。
